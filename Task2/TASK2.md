# Task 2. Проектирование решения с учeтом Privacy by Design

## Цель

Цель задания — спроектировать целевую C4-архитектуру системы «Медикаменте» с учeтом принципов Privacy by Design и заранее предусмотреть механизмы снижения рисков утечки персональных, медицинских, финансовых и аналитических данных.

## As-Is

В текущей архитектуре данные пациентов, медицинские карты, результаты анализов и документы хранятся в Excel-файлах, PDF/JPG-сканах и на общем файловом сервере.  
Доступ к данным контролируется в основном на уровне доменной аутентификации и общих папок.

В текущем состоянии отсутствуют:

- централизованное хранение данных пациентов;
- управление согласиями пациентов;
- полноценные RBAC/ABAC-механизмы;
- тегирование данных;
- Data Lineage;
- централизованный аудит доступа;
- мониторинг нетипичных действий;
- безопасный аналитический слой для BI/ML/AI.

## Основные риски

- хранение PII и PHI в Excel-файлах и сканах;
- несанкционированный доступ к медицинским данным;
- отсутствие контроля просмотра и изменения данных;
- отсутствие прозрачности движения данных между системами;
- избыточный сбор и передача данных;
- использование реальных данных в аналитике без обезличивания;
- отсутствие контроля передачи данных во внешнюю лабораторию;
- невозможность быстро выявить массовую выгрузку или нетипичный доступ.

## To-Be

В целевой архитектуре предложена единая цифровая платформа «Медикаменте» для управления клиентскими, медицинскими, финансовыми и аналитическими данными.

В архитектуру добавлены следующие блоки:

- Patient Portal (Клиентский портал);
- Employee Portal (Портал для сотрудников);
- API Gateway;
- IAM / Keycloak;
- Consent Management Service;
- CRM / Patient Service;
- Appointment Service;
- Medical Record Service;
- Laboratory Integration Service;
- Payment Service;
- Secure Document Storage;
- Data Catalog / Metadata / Tagging Service;
- Audit Log Service;
- SIEM / Monitoring / Alerting;
- Privacy-Preserving Analytics Layer.

## Privacy by Design механизмы

В целевой архитектуре реализованы следующие механизмы Privacy by Design:

- минимизация собираемых и передаваемых данных;
- доступ пациента только к собственным данным;
- разграничение доступа сотрудников по ролям и атрибутам через RBAC/ABAC;
- управление согласиями пациентов на обработку данных;
- централизованный вход через IAM / Keycloak;
- доступ ко внутренним сервисам только через API Gateway;
- тегирование данных: PII, PHI, LAB, FIN, HR, DOC, ANALYTICS, RAW, CONFIDENTIAL;
- шифрование данных при хранении на уровне БД и файлового хранилища;
- защищенная передача данных по TLS;
- централизованный аудит доступа и изменений;
- мониторинг нетипичных действий и событий безопасности;
- ограничение массовых выгрузок медицинских данных;
- обезличивание и маскирование данных перед использованием в аналитике;
- хранение метаданных и Data Lineage для прозрачности движения данных.

## Аналитический слой

Для аналитической работы предложен отдельный слой:

**Privacy-Preserving Analytics Layer**

Он предназначен для безопасной подготовки данных для BI, ML и AI без прямого доступа аналитиков к персональным и медицинским данным.

Слой включает:

- Data Ingestion / ETL;
- Data Lake: Raw Zone;
- Data Masking / Anonymization Service;
- Data Lake: Trusted / Cleansed Zone;
- Data Mart / BI Zone;
- BI / ML / AI Workspace;
- Data Lineage / Metadata.

Данные из операционных сервисов сначала поступают в ETL, затем сохраняются в Raw Zone, проходят обезличивание и минимизацию, после чего попадают в Trusted / Cleansed Zone и Data Mart / BI Zone.

BI Analyst / Data Analyst работает только с обезличенными или агрегированными данными через BI / ML / AI Workspace. Прямой доступ к PII и PHI в аналитическом слое запрещен.

## Результат

Целевая архитектура снижает риски утечки конфиденциальных данных, вводит контроль доступа, аудит, тегирование, мониторинг и прозрачность потоков данных.

Решение позволяет безопасно развивать клиентский портал, мобильное приложение, интеграцию с лабораторией и аналитические сервисы на базе BI, ML и AI.
